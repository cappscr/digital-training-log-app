# User Settings

Related intent: [`intent/user_settings/intent.md`](../../intent/user_settings/intent.md)

## Summary

Signed-in users get a Settings page in place of the current profile page. The page edits the user's name and four training preferences: the day a microcycle starts, and the default units for weight, distance, and elevation. One Save writes the name and those preferences together.

Preferences are defaults for new entry. They do not rewrite sessions already stored. Theme is stored on the settings row and is not shown or applied in this slice.

## Outcomes (acceptance)

A signed-in user can:

1. Open Settings from the nav item that today says Profile.
2. See their name in an editable field and their email in a disabled field.
3. Choose a microcycle start day and default units for weight, distance, and elevation.
4. Save the name and those four preferences with one button.
5. Open a new training session with those units already selected.
6. Open the pace calculator, while signed in, with pace units that follow the distance setting.
7. Add a new strength set or exercise that starts with their weight unit.

Out of scope for this slice:

- A collapsible sidebar.
- Moving the theme toggle onto Settings, or reading `theme` from the API in `ThemeProvider`. Theme stays on `localStorage`.
- Editing email or password.
- Redesigning any other page.
- Using `microcycle_start_day` in training-session pagination.
- Converting units on sessions, exercises, or pace results that are already saved.

## Domain model

`User` has one `UserSetting`. Create the row in the same transaction as the user. A migration backfills one row for every existing user.

| Field | Type | Required | Default | Allowed values |
| --- | --- | --- | --- | --- |
| `microcycle_start_day` | string | Yes | `monday` | `sunday`, `monday` |
| `default_weight_unit` | string | Yes | `lbs` | `lbs`, `kg` |
| `default_distance_unit` | string | Yes | `mi` | `mi`, `km` |
| `default_elevation_unit` | string | Yes | `ft` | `ft`, `m` |
| `theme` | string | Yes | `dark` | `light`, `dark`, `system` |

Use the same unit strings the training forms already persist. Store `theme` so the next issue can move the toggle, and do not accept it on the update endpoint in this slice.

`user_id` is unique. Primary key is a string UUID, generated by the database because the server creates the row. Destroy the settings row with the user.

Name validation stays as specified in [`spec/users/spec.md`](../users/spec.md): present, 50 characters or fewer. Email is not writable here.

## API

### Read

Include `settings` on `UserSerializer`, so `GET /api/v1/users/me`, login, and signup responses carry it.

```json
{
  "id": "<uuid>",
  "name": "Chris Capps",
  "email": "chris@example.com",
  "settings": {
    "microcycle_start_day": "monday",
    "default_weight_unit": "lbs",
    "default_distance_unit": "mi",
    "default_elevation_unit": "ft",
    "theme": "dark"
  }
}
```

### Update

`PATCH /api/v1/users/me`, login required. This is the only new endpoint. It updates the current user's name and settings. It does not accept another user's id.

```json
{
  "user": {
    "name": "Chris Capps",
    "microcycle_start_day": "monday",
    "default_weight_unit": "lbs",
    "default_distance_unit": "mi",
    "default_elevation_unit": "ft"
  }
}
```

Permit `name` and the four settings fields. Do not permit `email`, `password`, `password_confirmation`, `theme`, or `id`.

Success is 200 and the user payload above. Invalid name or settings values are 422 problem+json. A missing current user is the existing login failure.

`GET /api/v1/users/:id` stays. The frontend stops using it as a page.

## Frontend

### Route and nav

Replace the `/users/:id` page with `/settings` inside `AppLayout`.

- The signed-in nav item is labeled Settings and points at `/settings`. Desktop and mobile nav share that list.
- A signed-in visit to `/login` redirects to `/settings` instead of `/users/:id`.
- The login form still lands on `/training-sessions`.
- Remove `UserProfilePage` and `UserSidebar`. Remove `Gravatar` if nothing else imports it.

A signed-out visit to `/settings` redirects to `/login`.

### Settings page

One form. Two sections. Match the training-sessions page width and title treatment. Do not restyle other pages.

**Profile**

- Name: text input, required.
- Email: text input, disabled, filled from the current user, not submitted.

**Training**

Each control is a single-select `ToggleGroup`. A group always has one value; the user cannot clear it.

| Label | Options |
| --- | --- |
| Week starts on | Sunday, Monday |
| Weight | lbs, kg |
| Distance | mi, km |
| Elevation | ft, m |

One Save button submits the name and the four groups. Disable it while the request is in flight. On success, stay on the page and show a success toast. On 422, show the field errors. Update the current-user cache from the response so open forms see the new defaults.

Do not render a theme control.

### Where the defaults apply

Read settings from the current user. Logged-out screens keep today's hardcoded defaults.

| Surface | Create or add | Edit an existing record |
| --- | --- | --- |
| New training session, including a sport switch on that form | `distance_unit`, `elevation_unit`, and `weight_unit` from settings | Stored `distance_unit`, `elevation_unit`, and `weight_unit` stay as saved. A null stored unit stays empty rather than being filled from settings, so a save does not stamp a unit onto an old row. |
| New strength set or exercise, including one added while editing a session | `weight_unit` from settings | An existing set keeps its stored `weight_unit`. |
| Pace calculator | Signed in: `mi` → `per_mile`, `km` → `per_km`. Signed out: `per_mile` | The calculator does not edit a saved record. The user can still change the unit for that calculation. |

`microcycle_start_day` is shown and saved only. Training-session pagination does not read it.
